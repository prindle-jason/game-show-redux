# Future enhancements

Deferred decisions and known gaps, tracked here instead of scattered as footnotes across other docs. Not scheduled — pull an item into a milestone doc when it's actually being built.

- **Server-issued room codes.** Right now a room is created implicitly by whoever is first to join a given code, typed by hand into `player-app`. A server-minted code (e.g. a word-pair or alphanumeric code, via an HTTP route on `party`) plus a shareable join link is planned, but wasn't built as part of the room-shell milestone so it wouldn't constrain that milestone's UI.
- **Durable room state.** `party`'s room state currently lives only in the Durable Object's in-memory JS state, not `ctx.storage`. An idle room being evicted, an error, or a Worker redeploy wipes it entirely — reconnecting looks like joining a brand-new empty lobby, not resuming a game in progress. Making this durable means persisting `RoomState` to `ctx.storage` on every change and restoring it when a fresh DO instance spins up.
- **Resolve media URLs at clue-pick time, not add-to-queue time.** Media currently uploads and gets resolved into contestant views as soon as a round is queued (see [requirements.md](./requirements.md#media)), so contestants' browsers can prefetch during the lobby and the media-ready gate before each round clears almost instantly. The trade-off: a contestant could inspect the page and view upcoming clue media before it's picked. Accepted for now since it's a game-night, no-accounts setting; the fix is contained — delay URL resolution into contestant views until the clue is actually picked, and the round wouldn't go `active` until *that* client fetches it. The readiness barrier, `round-media-ready` message, and prefetch-to-blob mechanism (see the media-upload milestone) wouldn't need to change, only when resolution happens.
- **Expose the correct answer's content to contestants after judging.** Neither Jeopardy nor Final Jeopardy ever sends the round's canonical answer (`clue.answer`, text or media) to contestant views — only the host ever sees it, via its own `resolvedData`. For Final Jeopardy this is a simple fix: `resolvedData.answer` is already computed and sits right next to `resolvedData.clue`, so `toFinalJeopardyContestantView` just needs to expose it once `phase` reaches `revealing`/`summary`, the same gating `clue` already gets. For regular Jeopardy it's more involved: `judge`/`skip-clue` currently clear `activeClue` back to `null` in the same action that scores the answer, so there's no discrete "answer is being shown" window the way Final Jeopardy has `revealStage: hidden → answer → wager`. Fixing it means adding a `revealedAnswer` state field that `judge`/`skip-clue` set instead of nulling `activeClue`, a new host-only `dismiss-clue` action to actually close it out, and a host UI step in between judging and returning to the board — a real (if small) change to the host's flow, not just a wiring fix.
